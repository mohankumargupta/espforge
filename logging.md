# `logging.md`: Fine-Grained Logging Control & Subsystem Filtering in `espforge`

## 1. Context: The "Chatty Wi-Fi / Noisy Peripheral" Problem

In frameworks like ESPHome, setting log levels globally is a notorious friction point. Enabling Wi-Fi, MQTT, or complex bus drivers often floods the serial monitor with connection handshakes, state-machine transitions, ARP requests, and frame debugging. 

In `espforge`, the user currently has clean control inside `src/app.rs` via `ctx.logger` (or direct `log::*` invocations). However, **at the driver, peripheral, runtime, and third-party crate levels, logging is largely out of the user's direct control**.

### Where Do the Logs Come From?

When a project is generated by `espforge`, several distinct layers emit log records:

```
[Level 1: User App]          ──► app.rs (ctx.logger.info / log::info!)
[Level 2: espforge-runtime]  ──► wifi.rs ("wifi: connected", "wifi: disconnected, retrying")
[Level 3: Drivers]           ──► espforge-drivers / vendor crates (ssd1306, sky-ili9341, sntpc, etc.)
[Level 4: Protocol Stacks]   ──► smoltcp, embassy-net, edge-http, edge-ws, embedded-tls
[Level 5: Silicon Subsystem] ──► esp-radio (Wi-Fi/BT baseband PHY), esp-rtos (embassy tick), esp-hal
```

Today, even on a minimal Wi-Fi project (`05.Networking/wifi_station`), a user observing the serial monitor receives logs from `esp-radio`, `esp-rtos`, `esp-println`, `smoltcp`, and `espforge-runtime` before `app::setup()` has even finished executing.

---

## 2. Current Logging State in `espforge`

To understand how to gain control, we examine how logging is currently hooked up:

1. **Hardcoded Dependencies & Cargo Features (`espforge-emit/src/codegen/cargo.rs`):**
   * `esp-hal`, `esp-rtos`, `esp-radio`, `esp-bootloader-esp-idf`, and `esp-println` all have `log-04` features **unconditionally enabled**.
   * `embassy-executor`, `embassy-time`, `embassy-net`, and `smoltcp` all have `log` features **unconditionally enabled**.
2. **Hardcoded Logger Initialization (`espforge-emit/src/codegen/rust.rs`):**
   * Generated `src/bin/main.rs` contains:
     ```rust
     #[esp_hal::main] // or #[esp_rtos::main]
     fn main() -> ! {
         esp_println::logger::init_logger_from_env();
         ...
     ```
3. **Hardcoded Environment Default (`espforge-emit/src/codegen/config.rs`):**
   * `.cargo/esp-config.toml` is emitted as a static `SeedOnce` file containing:
     ```toml
     [env]
     ESP_LOG="info"
     ```
4. **Thin Runtime Wrapper (`espforge-runtime/src/lib.rs`):**
   * `Logger` simply forwards directly to the global `log` facade:
     ```rust
     pub struct Logger;
     impl Logger {
         pub fn info(&self, msg: impl core::fmt::Display) { log::info!("{}", msg); }
         pub fn warn(&self, msg: impl core::fmt::Display) { log::warn!("{}", msg); }
         pub fn error(&self, msg: impl core::fmt::Display) { log::error!("{}", msg); }
     }
     ```

---

## 3. Three Strategies for Fine-Grained Logging Control

Here are three distinct architectural strategies to achieve true `level="none"` and selective per-driver/subsystem logging.

---

### Strategy 1: Declarative Module-Target Filtering via `ESP_LOG` & Cargo Config (The Native Backend Approach)

#### Mechanics
`esp_println::logger::init_logger_from_env()` uses `esp-println`'s built-in target filtering (heavily inspired by `RUST_LOG`). It evaluates `ESP_LOG` at compile-time/run-time using commas, target prefixes, and log levels:
```text
ESP_LOG="off,hello_world::app=info,espforge_drivers::ssd1306=debug"
```

#### Specification in `.espf`
Add a `<logger>` element under `# espforge` (or configure it via `<options>`):
```xml
# espforge
  <project name="sensor_station" />
  <chip type="esp32c3" />
  <runtime type="embassy" />
  <logger default="none" />
    <log_filter target="app" level="info" />
    <log_filter target="scd4x" level="debug" />
    <log_filter target="wifi_station" level="warn" />
```

#### Compiler & Codegen Implementation
1. **Target Mapping Table in `espforge-elements`:**
   Map semantic targets (`app`, `wifi_station`, driver tags like `ssd1306` or `scd4x`) to Rust module paths:
   * `"app"` $\to$ `<crate_name>::app`
   * `"wifi_station"` $\to$ `espforge_runtime::hw::wifi,esp_radio`
   * `"ssd1306"` $\to$ `espforge_drivers::ssd1306,ssd1306`
   * `"scd4x"` $\to$ `espforge_drivers::scd4x`
   * `"network_stack"` $\to$ `smoltcp,embassy_net`
2. **Dynamic Generation of `[env] ESP_LOG` in `.cargo/esp-config.toml`:**
   Generate the filter string:
   ```toml
   [env]
   ESP_LOG = "off,sensor_station::app=info,espforge_drivers::scd4x=debug,espforge_runtime::hw::wifi=warn,esp_radio=warn"
   ```

#### Evaluation
* **Pros:** 
  * Zero changes needed in `espforge-runtime` or driver crates; leverages `esp-println`'s existing parser.
  * Solves the problem immediately at the filtering layer.
* **Cons:** 
  * `.cargo/esp-config.toml` is currently `Ownership::SeedOnce`. If a user updates their `.espf`, `espforge` would not overwrite `esp-config.toml` unless its ownership model is changed to `Merged` or `Owned`.
  * Flash bloat: Format strings from quiet crates (`esp-radio`, `smoltcp`) still get compiled into `.rodata` in Flash; they are only dropped at runtime when checking the filter.

---

### Strategy 2: Compile-Time Feature Stripping & `log` Release Level Gating (The Zero-Cost / Flash-Pruning Approach)

#### Mechanics
In embedded Rust, `log` macros (`info!`, `trace!`) compile formatting logic and static strings directly into the binary. To achieve true `level="none"` where logging produces **zero binary bloat and zero CPU cycles**, logging must be stripped at compile time.

The `log` crate provides built-in compile-time gating features:
* `max_level_off`, `max_level_error`, `max_level_warn`, `max_level_info`
* `release_max_level_off`, etc.

Additionally, third-party crates (`esp-hal`, `esp-radio`, `smoltcp`, `embassy-net`) only emit logs if their `log` or `log-04` Cargo features are turned on.

#### Specification in `.espf`
```xml
# espforge
  <project name="silent_tracker" />
  <chip type="esp32c3" />
  <runtime type="embassy" />
  <options logging="none" /> <!-- or logging="minimal", logging="full" -->
```

#### Compiler & Codegen Implementation
In `espforge-emit/src/codegen/cargo.rs`:
1. When `opts.value("logging") == "none"`:
   * Add feature to `log` dependency:
     ```toml
     log = { version = "0.4.27", features = ["max_level_off", "release_max_level_off"] }
     ```
   * Strip `"log-04"` from `esp-hal`, `esp-rtos`, `esp-radio`, `esp-println`.
   * Strip `"log"` from `embassy-executor`, `embassy-time`, `embassy-net`, `smoltcp`.
2. When `opts.value("logging") == "drivers_only"`:
   * Keep `"log-04"` active on `espforge-drivers` and user app.
   * Strip `"log"` from `smoltcp` and `esp-radio`.

#### Evaluation
* **Pros:** 
  * **Absolute silence.** Dead code elimination strips all log formatting functions and strings from Flash memory.
  * Dramatic Flash size reduction (Wi-Fi + TLS projects can save 30–70 KB of flash).
* **Cons:** 
  * Coarse-grained. Cargo features are crate-wide and cannot differentiate between two drivers in the same crate (unless drivers are in separate crates, as designed in Phase 8).
  * Feature unification: if any sub-dependency enables `log`, compile-time stripping on downstream crates can be overridden unless `max_level_off` is forced on `log`.

---

### Strategy 3: Dedicated `espforge` Log Filter Engine with Tag-Aware Dispatch (The Structured Context Approach)

#### Mechanics
Instead of delegating logger filtering to `esp-println`'s static environment variable, `espforge-runtime` implements its own `log::Log` backend wrapper that sits between the `log` facade and `esp_println::println!`.

```
                    ┌────────────────────────┐
                    │      log::Record       │
                    └───────────┬────────────┘
                                │
                                ▼
            ┌────────────────────────────────────────┐
            │   espforge_runtime::FilteredLogger     │
            ├────────────────────────────────────────┤
            │  Rules:                                │
            │  - Default Level: Warn                 │
            │  - Tag "app"        => Info            │
            │  - Tag "scd4x"      => Debug           │
            │  - Crate "smoltcp"  => Off             │
            │  - Crate "esp_radio"=> Error           │
            └───────────────────┬────────────────────┘
                                │ (If Allowed)
                                ▼
                   esp_println::println!()
```

#### Specification in `.espf`
```xml
# espforge
  <project name="smart_plug" />
  <chip type="esp32c3" />
  <runtime type="embassy" />

# peripherals
  <wifi id="radio" log="error" /> <!-- Direct log level on the silicon block -->

# devices
  <ssd1306 id="oled" bus="$i2c0" log="info" />
  <scd4x   id="air"  bus="$i2c0" log="debug" />

# services
  <wifi_station id="home" wifi="$radio" log="warn" />
```

#### Compiler & Codegen Implementation
1. **Emitted Filter Table in `src/generated.rs`:**
   Generate a static lookup table mapping targets to level filters:
   ```rust
   // src/generated.rs
   pub static LOG_FILTERS: &[(&str, log::LevelFilter)] = &[
       ("smart_plug::app", log::LevelFilter::Info),
       ("espforge_drivers::ssd1306", log::LevelFilter::Info),
       ("espforge_drivers::scd4x", log::LevelFilter::Debug),
       ("espforge_runtime::hw::wifi", log::LevelFilter::Warn),
       ("esp_radio", log::LevelFilter::Error),
       ("smoltcp", log::LevelFilter::Off),
   ];
   ```
2. **Logger Initialization in `main.rs`:**
   Instead of `esp_println::logger::init_logger_from_env()`, generate:
   ```rust
   espforge_runtime::init_logger(log::LevelFilter::Warn, LOG_FILTERS);
   ```

#### Evaluation
* **Pros:**
  * **Ergonomic, declarative, per-component syntax:** Users configure `log="error"` directly on the peripheral or device tag.
  * Completely bypasses `.cargo/esp-config.toml` caching / `SeedOnce` obstacles.
  * Works uniformly across blocking and Embassy runtimes.
* **Cons:**
  * Requires writing a custom `log::Log` implementation (~80 lines of Rust in `espforge-runtime`).
  * Small CPU overhead during log dispatch (string prefix matching on module paths before printing).

## 4. Deep Architectural Analysis: Why Is This Tricky in `espforge`? (The Obstacles)

Implementing granular logging in `espforge` exposes several underlying architectural hurdles:

### Obstacle 1: The `.cargo/esp-config.toml` `SeedOnce` Dilemma
In `espforge-emit/src/codegen/plan.rs`, `.cargo/esp-config.toml` is defined with `Ownership::SeedOnce`:
```rust
PlannedFile {
    out_path: ".cargo/esp-config.toml",
    source: Source::EspConfig,
    ownership: Ownership::SeedOnce,
}
```
* **The Failure:** If logging configuration is passed via `ESP_LOG` in `esp-config.toml`, any change to the `.espf` spec will **never update** `esp-config.toml` on subsequent `espforge build` runs! `SeedOnce` files are written only when absent.
* **Why it's tricky:** Changing `esp-config.toml` to `Ownership::Owned` or `Merged` conflicts with the design principle that `esp-config.toml` is meant for user-edited environment variables (`[env] ESP_LOG="info"`).

### Obstacle 2: Monolithic Feature Coupling in `espforge-emit`
In `espforge-emit/src/codegen/cargo.rs`, the generation of dependencies unconditionally bakes in logging:
```rust
let mut hal = vec![chip_name];
if opts.is_on("unstable-hal") { hal.push("unstable"); }
hal.push("log-04"); // HARDCODED!
deps["esp-hal"] = Item::Value(dep("~1.2.2", &hal));
```
The emitter has no concept of conditional feature exclusion. If a user sets `level: none`, `cargo.rs` currently lacks the pipeline connections to omit `"log-04"` from `esp-hal`, `esp-rtos`, `esp-radio`, or `"log"` from `smoltcp`.

### Obstacle 3: Semantic Dissociation Between ESPF Tags and Rust Module Names
In `.espf`, elements are identified by user IDs:
```xml
<wifi_station id="home" wifi="$radio" />
<ssd1306 id="oled" bus="$i2c0" />
```
However, the noisy log messages are emitted by deep third-party module targets:
* The radio logs as: `esp_radio::wifi::*`
* The TCP stack logs as: `smoltcp::wire::*` or `smoltcp::socket::*`
* The display logs as: `ssd1306::*`

Because `espforge` abstracts these third-party crates away so the user doesn't have to manage them, the compiler must maintain a complex, brittle dictionary translating user-level entity tags into crate-level logger target strings.

### Obstacle 4: `espforge-runtime` Emits Direct Unfiltered Logs
In `espforge-runtime/src/hw/wifi.rs`:
```rust
log::info!("wifi: connected");
...
log::warn!("wifi: disconnected, retrying");
```
And in `espforge-runtime/src/services/ws_client.rs`, `http_client.rs`, etc.
Because these calls use the generic `log::*` macros without a custom target override (e.g. `log::info!(target: "espforge::wifi", ...)`), their target defaults to the module path (`espforge_runtime::hw::wifi`). Without a centralized filtering dispatcher, these cannot be suppressed independently of user app logs.

### Obstacle 5: Target Architecture Variance (Xtensa vs. RISC-V String Formatting)
`no_std` string formatting on embedded RISC-V and Xtensa cores is expensive. On smaller chips like ESP32-C2 or ESP32-C3, linking in formatting routines for `Display` representations of network packets, Wi-Fi errors, and HAL bus errors eats a substantial portion of the 384 KB / 400 KB SRAM. Runtime filtering (Strategies 1 & 3) drops the text at the UART boundary, but **cannot recover the Flash or RAM wasted by formatting code**.

---

## 5. Recommended Technical Blueprint

The optimal architecture combines **Strategy 2 (Compile-time Flash stripping)** for when the user wants absolute silence, with **Strategy 3 (Tagged Runtime Dispatcher)** for selective debugging.

### Phase 1: Support `<logger>` in `# espforge` (Grammar & Schema)
Extend `espf.schema.kdl`:
```kdl
element "logger" section="espforge" {
    summary "Global log filter and serial logging configuration"
    attr "level" kind="choice" default="info" {
        choices "none" "error" "warn" "info" "debug" "trace"
    }
    attr "drivers" kind="choice" default="inherit" {
        choices "inherit" "none" "error" "warn" "info" "debug" "trace"
    }
    attr "network" kind="choice" default="inherit" {
        choices "inherit" "none" "error" "warn" "info" "debug" "trace"
    }
    attr "hal" kind="choice" default="warn" {
        choices "inherit" "none" "error" "warn" "info" "debug" "trace"
    }
    example "silent" #"<logger level="none" />"#
    example "app_only" #"<logger level="info" network="none" hal="none" drivers="none" />"#
    example "debug_sensors" #"<logger level="warn" drivers="debug" />"#
}
```

### Phase 2: Add Target-Filtering Logger to `espforge-runtime`
In `espforge-runtime`:
1. Provide `espforge_runtime::logger::init(config)` which wraps `esp_println`:
   ```rust
   pub struct FilterRule {
       pub prefix: &'static str,
       pub level: log::LevelFilter,
   }

   pub fn init_logger(default_level: log::LevelFilter, rules: &'static [FilterRule]);
   ```
2. When `record.level() <= target_level_for(record.target())`, emit via `esp_println::println!`.

### Phase 3: Update `espforge-emit` Codegen
1. If `<logger level="none" />` is set:
   * Activate `log/max_level_off` in `Cargo.toml`.
   * Strip `"log-04"` and `"log"` features from all dependencies.
   * Emit `// logger disabled` in `main.rs` instead of `init_logger`.
2. If custom filters are set:
   * Emit the `FilterRule` array in `src/generated.rs`.
   * Map `network="none"` to prefixes `esp_radio`, `smoltcp`, `embassy_net`, `espforge_runtime::hw::wifi`.
   * Map `drivers="debug"` to prefixes `espforge_drivers`, and specific driver crates.

This design gives the user **true `level: none` that strips code from flash**, while preserving the ability to turn on debug diagnostics exclusively for a stubborn sensor without drowning in Wi-Fi and TCP packet logs.
