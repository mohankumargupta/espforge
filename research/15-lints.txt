Applying Lauren Tan’s "environment over prompts" approach, automatic lint rules in espforge would act as deterministic guardrails that stop AI agents—and human contributors—from introducing architectural drift, broken driver glue, or no_std incompatibilities before a slow embedded cross-compilation even runs.
Because espforge is a multi-crate Rust workspace (espforge-core, espforge-drivers, espforge-emit, etc.) that generates no_std esp-hal projects from .espf and .kdl manifests, custom lints (via workspace clippy.toml rules, dylint, or cargo xtask checks) can enforce domain-specific invariants directly inside the repository:

1. Enforcing Workspace & Boundary Architecture

• Preventing Crate Leakage: espforge cleanly separates parsing (espforge-schema), diagnostics (espforge-diagnostics), and code generation (espforge-emit). Custom lints can block espforge-schema from importing espforge-emit or runtime dependencies, ensuring AI agents don't create circular dependencies or tangle parsing with code emission.
• Protecting Generated Output Invariants: Since build/ is disposable output generated by espforge-emit, lints on the emitter crate can enforce that generated src/app.rs and Cargo.toml templates never emit std-only crates or blocking calls inside embassy async templates.

2. Catching Embedded & no_std Traps Instantly

• Banning std and Heap Allocations in Runtime Crates: AI agents frequently default to standard Rust idioms (String, Vec, println!, std::time::Duration). Strict clippy::disallowed_methods and clippy::disallowed_types rules on espforge-runtime and espforge-elements immediately reject heap allocations or panicking unwraps (clippy::unwrap_used) that would crash bare-metal ESP32 targets.
• Hardware Pin & Peripheral Safety: Lints can verify that peripheral abstractions in espforge-elements follow consistent ownership patterns so agents don't generate code that attempts to clone or double-borrow singleton esp-hal peripherals.

3. Replacing Markdown Docs with Enforceable Driver Checks

• Turning .md Plans into Code Rules: The repository currently contains planning and fix logs (driverfixes.md, drivergaps.md, driverglue.md, plandriverfixes.md). Following Lauren Tan’s principle of replacing comments and prose with enforceable checks, any rule discovered while fixing driver glue can be codified into a lint or espforge driver verify check.
• Validating .kdl Manifests and env: Substitutions: Automated checks can lint bundled manifests (espforge-drivers/manifests/*.kdl) and examples (espforge-examples) to ensure every driver attribute matches the schema, no hardcoded secrets leak into .espf files instead of env:NAME substitutions, and every example compiles cleanly for both blocking and async runtimes.

4. Accelerating the Agent Verification Loop

• Fast Feedback Before Cross-Compilation: Compiling esp32 / esp32c3 targets (especially Xtensa toolchains) is slow. Fast AST-level lint checks give an AI agent sub-second feedback on structural mistakes—such as bad error-handling patterns that bypass espforge-diagnostics—so the agent self-corrects before running espforge build or Wokwi simulations.
